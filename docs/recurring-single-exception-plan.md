# 循环日程单次例外方案（评审稿 v0.2，未实现）

> 状态：仅方案，等待评审后另行实现。本轮不修改事件结构、同步协议或客户端行为。

## 1. 结论与范围

“隐藏当天循环实例 + 新建普通替代日程”可行，并且比修改父系列规则更容易兼容现有渲染和同步。单次例外由以下两项共同表达：

1. 父循环日程在 `data.recurrenceExceptions[originalDate]` 写入隐藏标记；
2. 创建一条非循环普通日程，通过 `replacementOf` 指回父系列和原实例日期。

本方案只处理循环日程的某一次实例。Deadline、长期任务和普通日程不是循环实例，不复用该语义。

## 2. 身份与数据结构

- `seriesId`：父循环日程已有的稳定 `event_id`。
- `originalDate`：原实例在日历本地时区下的 `YYYY-MM-DD`，即使替代日程跨日移动也不改变。
- `exceptionKey`：`seriesId + ":" + originalDate`，仅作逻辑键。
- `replacementId`：以固定应用 namespace 对 `exceptionKey` 计算 UUIDv5。所有设备对同一实例生成相同 `event_id`，从而复用现有 `(user_id, event_id)` 唯一约束和版本冲突机制，避免随机 ID 产生双份替代日程。

父系列新增可选字段：

```json
{
  "recurrenceExceptions": {
    "2026-08-21": {
      "hidden": true,
      "replacementId": "deterministic-uuid",
      "updatedAt": "2026-08-20T08:00:00Z"
    }
  }
}
```

替代日程仍是普通事件，必须满足 `isRecurring=false`，并新增：

```json
{
  "replacementOf": {
    "seriesId": "parent-uuid",
    "originalDate": "2026-08-21"
  }
}
```

服务端和客户端只接受同一用户拥有的父系列；父系列必须存在且为循环日程，`originalDate` 必须确实命中当时的循环规则。不得跨用户解析或关联 `seriesId`。

## 3. 新建与跨日改期

客户端以一个 `exceptionKey` 状态机执行，两个写操作分别使用稳定、可重试的 `operationId`：

1. 对父系列做带 `baseVersion` 的更新，写入隐藏标记和确定性 `replacementId`；
2. 以 `replacementId` 创建普通替代日程。当天调整时 `date=originalDate`，跨日调整时 `date=targetDate`，但 `replacementOf.originalDate` 保持原值。

现有同步协议按事件逐条提交，不具备跨两条事件的原子事务。因此客户端必须把未完成步骤保存在同步 outbox，重启或断网恢复后继续：

- 只有隐藏标记：原实例已安全隐藏，重试创建替代日程；
- 只有替代日程：先补写隐藏标记；补写前渲染层按 `replacementOf` 临时抑制原实例，避免短暂重复；
- 两项都存在且关联一致：状态完成。

服务端若未来提供批量原子 push，可将两项放入同一事务，但这不是本方案上线的前置依赖。

## 4. 去重、幂等与并发冲突

- 同一 `exceptionKey` 的 `replacementId` 确定且唯一；重复创建会落到同一 `event_id`，不会形成第二条事件。
- `operationId` 继续保证单次写重试幂等，`baseVersion` 继续负责父系列和替代日程各自的乐观并发。
- 两台设备同时修改同一实例时，父系列更新或替代事件更新至少一项会发生版本冲突；客户端不得按“时间更新者自动获胜”静默覆盖，而应拉取服务器版本后让用户选择保留哪个目标日期/内容，再以新版本重试。
- 替代日程的 `replacementOf` 一经创建不可改为另一父系列或另一 `originalDate`；移动只修改普通日程的 `date/time`。

## 5. 查询与渲染

展开循环实例时，先检查父系列 `recurrenceExceptions[date].hidden`；为 `true` 则不生成原实例。替代日程按普通日程渲染在其实际 `date`，可显示“来自循环日程”的非阻塞标识。

渲染层以事件数据为准，不依赖仅存在于本机的缓存。异常恢复期间若替代事件存在但父隐藏标记尚未同步，按 `replacementOf(seriesId, originalDate)` 临时隐藏原实例。

## 6. 完成、撤销与删除

- 替代日程使用自身 `isCompleted`，不写入父系列 `completedDates`。
- 创建例外时若原实例已在父系列 `completedDates` 中，默认把完成状态复制给替代日程，并从父系列移除该日期；这两项也进入同一可恢复状态机。不得同时保留两份完成状态。
- “撤销例外并恢复原实例”：删除/墓碑化替代日程，移除父系列对应隐藏标记；若替代日程已完成，则将完成日期恢复到父系列的 `originalDate`。
- “仅删除这一次”：保留 `hidden=true`，删除/墓碑化替代日程，并清空 `replacementId`。
- 用户直接删除替代日程：解释为“保留隐藏，只删除替代”，界面另提供明确的“恢复原实例”。
- 删除父系列：由应用层生成对所有关联替代日程的删除操作；JSON 关联不是数据库外键，不能依赖数据库级联。离线设备以后推送孤立替代时，服务端校验失败或客户端同步后将其墓碑化。

## 7. 父系列规则变化

编辑父系列时间、标题等非规则字段时保留例外。修改开始日、结束日、重复类型或重复星期后，应重新校验所有 `originalDate`：

- 仍命中新规则：保留；
- 不再命中新规则：标记为 orphan，提示用户选择删除替代、转成无关联普通日程，或恢复旧规则；不得静默删除。

更改父系列 `event_id` 不受支持；复制系列必须生成新 ID，不能继承原系列例外。

## 8. 旧数据与迁移

- 无 `recurrenceExceptions` / `replacementOf` 的旧数据行为完全不变，不需要批量改写。
- 新字段位于现有 JSONB `data` 中，第一阶段无需数据库表迁移。
- 若曾产生随机 ID 的试验版替代日程，迁移时按 `(user_id, seriesId, originalDate)` 分组：保留最高已确认版本，将其复制/归并到确定性 `replacementId`，其余写墓碑，并输出冲突清单供人工确认。
- 180 天墓碑规则继续适用。替代事件墓碑未过期前，离线设备不得用旧版本把它复活。

## 9. 安全与校验边界

- 所有关联查询必须同时限定 `user_id`；错误响应不得泄露其他用户是否存在该 `seriesId`。
- 限制每个父系列的例外数量和单次 payload 大小，避免在父事件 JSON 中无限增长；建议达到阈值后提示拆分系列，具体阈值实施前压测决定。
- 日期必须严格校验为真实 `YYYY-MM-DD`；只使用日历本地日期，不用 UTC 时间戳推导 `originalDate`。
- 审计日志只记录事件 ID、动作和结果，不记录标题、备注或完整事件正文。

## 10. 实施顺序与验收

1. 先实现纯函数：确定性 ID、异常展开、关联校验和状态机恢复，并做单元测试。
2. 再接入本地 EventStore/sync outbox；不改变现有云端 OpenAPI 前先完成离线/重启恢复测试。
3. 最后增加 AI 工具参数，使“只改这一次”明确生成单次例外动作，仍需用户审批后执行。

必须独立验证：当天修改、跨日修改、双设备并发、重复重试、两步间断网/崩溃、撤销、仅删除一次、完成状态转移、父规则变更、父系列删除、180 天墓碑、旧数据零迁移、跨用户伪造关联、日志无正文。全部通过前不得宣称例外功能完成。
